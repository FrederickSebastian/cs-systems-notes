
## 端口

1. 0-1023是HTTP, SSH等协议广泛使用的端口, 一般不建议使用他们作为端口(可以以管理员身份强制使用)
2. 1024-65535是操作系统动态分配的端口号. 
3. 使用`cat /etc/services`可以查看一些协议常用的端口号. 
4. 一个进程可以bind多个端口号.
5. 一般情况下一个端口不允许被多个进程bind, 一下情况除外:
	- 不同协议绑定同一个端口
	- 使用不同ip
	- 设置了端口复用

# UDP协议

## 特点

- 无连接: 拥有对端IP与Port即可传输, 不需要建立连接. 
- 不可靠
- 面向数据报: 一个报文必须被一次性全部发送, 不会拆分, 也不会合并. 一般情况下, 一个报文最大长度为64Kb(包括其首部)

请注意, 虽然在内核中实现了对于UDP的发送缓冲区结构, 但是UDP并不会使用它. 通常, 调用`sendto`会直接把报文交给内核. 
*其接收缓冲器不保证接收顺序, 并且如果已满, 会丢弃后续到达的数据*


## 报文结构

1. 16位源端口号
2. 16位目的端口号
3. 16位数据检验和
4. 16位UDP长度(整个报文的长度)

其报文在内核中实现为结构体. 


# TCP协议
TCP 全称为 "传输控制协议( Transmission Control Protocol ")

## 协议段格式补充
1. 32位序号: 标识本报文段中第一个数据字节的序号，用于保证数据有序传输. 由于一个数据块被分为多次发送, 协议并不保证client段的接收顺序, 故用该序号标识其原本的发送顺序. 
2. 32位确认序号: 表示期望收到对方下一个数据字节的序号
3. 16位窗口大小
4. 16位紧急指针

## 为什么是三次握手建立连接
三次握手验证了以下问题: 双方的通信意愿与网络概况
1. 三次握手可以充分验证双方都有收数据与发数据的能力. 如果仅有两次握手, 则不能验证双方均有收与发的能力
2. 验证网络的连通性

## 超时重传机制
如果一个报文在发出以后的一段时间内没有收到对端的应答, Server将认为报文可能丢失. 具体情况需要分为ACK确认应答丢失和Server发送的报文丢失. 故需要超时重传机制. 
*通常, 超时重传的时间间隔是动态变化的, 由内核根据网络状况计算. 累计到一定重传次数会关闭连接*
*如果是对端的应答报文丢失, 报文重传会导致重复接收. 序列号在此时有去重效果.*

## 半关闭
在首先发起断开连接请求的一方收到ACK以后, 该方进入半关闭状态: 不再发送数据, 但是仍然可以接收数据. 

Linux 提供 shutdown() 系统调用：其作用是关闭 Socket 的发送方向，保留接收方向。

## CLOSE_WAIT状态
CLOSE_WAIT 的核心意义是解决 TCP 被动关闭方仍有数据需要发送的问题，使双方能够独立、可靠地结束各自的发送方向。


## TIME_WAIT状态
TCP协议规定,主动关闭连接的一方要处于TIME_ WAIT状态,等待2个MSL(maximum segment lifetime)的时间后才能回到CLOSED状态.

在TIME_WAIT期间, 该端口不能被监听. MSL在RFC1122中规定为两分钟. 设置端口复用可以规避该问题. 

**TIME_WAIT状态解决了什么问题**
1. 确保对端接收到ACK报文并关闭. 如果ACK丢失, 对端不会关闭. 如果没有TIME_WAIT, 本机直接关闭连接, 会导致四次挥手没有正确完成. 
2. 由于报文可能在网络回环中多次传递而没有到达对端, 等待时间内可以让回环报文充分被丢弃而减少网络负担. 

## 滑动窗口机制
由于IPv4规定数据报最大长度：65535 字节, 故TCP 报文段的理论最大长度为65535-20=65515字节. 发送缓冲区用滑动窗口实现数据的分段与多次发送. 


在缓冲区内使用两个指针标识滑动窗口的起始与末尾地址. 滑动窗口的大小取决于对端接收缓冲区的大小. 当发送数据报到达对端时, 对端返回的ACK报文携带的确认序号反映了对端接收数据的情况. 根据对端接收数据的情况, 滑动窗口的起始地址右移. 根据对端的缓冲区大小, 滑动窗口的末尾地址右移. 

**滑动窗口不会左移**

## 快重传机制
快重传（Fast Retransmit） 是 TCP 的一种丢包恢复机制，目的是在重传计时器超时之前，尽早重传丢失的报文段，提高传输效率。
1. 发送方连续发送多个 TCP 报文段。
2. 如果某个报文段丢失，接收方收到后续失序报文段时，会重复发送对丢失数据的确认号（重复 ACK）。
3. 当发送方收到 3 个重复 ACK 时，就认为相应报文段可能丢失。
4. 发送方立即重传该报文段，无需等待超时计时器到期。

## 流量控制
接收端处理数据的速度是有限的. 如果发送端发的太快, 导致接收端的缓冲区被打满, 这个时候如果发送端继续发送, 就会造成丢包, 继而引起丢包重传等等一系列连锁反应. 造成网络资源的浪费.

对端通过回传自己的缓冲区大小使发送端控制发送的大小与速度. 从而达到流量控制的目的

## 拥塞控制
*如果网络拥堵时发送端仍然发送大量数据, 会导致拥塞现象更加严重. 故发送端需要根据网络状况控制发送速度.*

TCP引入**慢启动**机制, 完全发送所有数据前先发送少量不携带数据的报文检查网络状况. 通过特定算法以某种速度发送报文从而检测拥堵状况与网络承受上限. 

## 延迟应答
接收端接收到多个数据报文时只发送一个应答报文. 该报文携带的是收到的连续的(未丢失的)报文的最后一个确认序号. 如果多个报文中间有一个报文丢失, 则发送的是未丢失的前一个报文的确认序号. 

## 捎带应答
适用于双方互相发送数据的情况. 接收端在向发送端发送数据的同时携带对于上一个报文的确认信息(确认标志位等)

## 面向字节流与TCP
**TCP 是面向字节流的，指 TCP 将应用层交付的数据看作一连串无结构的字节序列进行传输，不保留应用层数据的消息边界.**TCP的数据分段多次传输, 并通过序号、确认和重传机制，保证数据可靠、有序地到达接收方。

## 粘包问题
TCP 粘包问题是指由于 TCP 是面向字节流的协议，不保留应用层消息边界，导致接收方一次读取的数据中可能包含多个应用层消息，无法直接区分各个消息的边界。
1. TCP协议头中没有包含全部报文大小的字段
2. 多个较小的数据段可能被合并到一个报文中发送. 
**解决方案**
该问题通常由应用层解决. 常见的方法包括但不限于在数据报头部约定本次发送数据的大小或使用明确的分隔符表明数据的结束位置. 具体参考HTTP协议的实现

### 异常
如果发生异常导致没有正常关闭连接, 会导致双方资源异常占用等问题.
1. 进程终止: 进程终止会自动关闭文件描述符, 从而触发四次挥手, 此时双方正常关闭连接. 
2. 主机正常关机: 同进程终止. 
3. 网络异常断开: TCP内置保活定时器, 会定期清理不活跃连接.同时部分应用层也实现了该机制. 

## 补充: 守护进程

如何把一个网络服务变为守护进程?

*核心是将其从当前登入的会话中脱离*
1. 先脱离当前进程组. 由于只含有一个进程的进程组, 该进程就是该进程组的组长. 故需要fork创建子进程
2. 创建子进程并调用`setsid()`使其脱离当前会话
3. 结束父进程

或者调用sys_call: `daemon()`使得该进程直接守护进程化.
