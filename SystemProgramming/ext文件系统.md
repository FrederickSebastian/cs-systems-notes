**文件系统格式化（如 `mkfs.ext4`）的本质是在目标设备上建立文件系统的管理结构。** 它不同于分区，也不意味着把整个设备上的旧数据逐字节清零。

本文介绍 ext 系列的基本组织方式；涉及块映射时，需要区分 ext2/ext3 的传统方案与 ext4 常用的 extent 方案。

## 基本概念

1. **分区（partition）**：通过分区表划分出的磁盘逻辑区域，可以作为建立文件系统的目标。分区不等于文件系统；文件系统也可以建立在整个设备、逻辑卷等目标上。
2. **块（block）**：文件系统分配和管理存储空间的基本单位，由格式化时选定的块大小决定，常见大小为 4 KiB。文件系统块不同于设备的扇区，一个块通常包含多个扇区。块既可以存放文件内容，也可以存放文件系统元数据。
3. **inode（索引节点）**：保存一个文件对象的属性及内容定位信息的结构。目录也是文件对象，也有 inode；文件名保存在目录项中。

## Block Group 结构

ext 文件系统将存储空间划分为多个块组（block group），以便管理空间，并尽量将相关的 inode 和数据块分配在相近的位置。

下面是传统块组布局的简化示意；超级块和 GDT 不一定出现在每个块组中，也省略了预留区域：

```text
| super | GDT | block  | inode  | inode | Data   |
| block |     | bitmap | bitmap | table | blocks |
```

1. **superblock（超级块）**：记录整个文件系统的 inode 总数、块总数、块大小、支持的特性等重要信息。主要超级块位于文件系统开头附近，备份副本分布在其他特定块组中；不是一个块组内保存多个超级块，也不是每个块组都必然有副本。
2. **GDT（Group Descriptor Table，块组描述符表）**：包含各块组的描述符，记录相应块组的块位图、inode 位图和 inode 表的位置，以及空闲块数、空闲 inode 数等信息。它描述块组，超级块描述整个文件系统。
3. **block bitmap（块位图）**：用位记录相应块组中哪些块已分配、哪些块空闲；文件系统元数据占用的块也需要计入。
4. **inode bitmap（inode 位图）**：用位记录相应块组中哪些 inode 已分配、哪些 inode 空闲。
5. **inode table（inode 表）**：保存该块组的磁盘 inode 记录。位图记录分配状态，inode 表保存实际的 inode 信息。
6. **data blocks（数据块区域）**：可存放普通文件内容、目录内容等；传统间接块映射所需的间接块也会占用块空间，并非全部都是用户文件内容。
7. 一个 ext 文件系统包含多个块组。ext4 的 `flex_bg` 等特性允许将多个块组的位图和 inode 表集中放置，因此实际布局不一定与示意图完全一致，应根据块组描述符定位。

## inode

1. 一个文件对象对应一个 inode，但多个文件名可以通过硬链接指向同一个 inode，不能把“一个文件名”与“一个 inode”当作一一对应关系。
2. 对于 ext2/ext3 的传统块映射，inode 中有 12 个直接块指针，以及一级、二级、三级间接块指针。直接指针指向数据块；间接指针先指向保存下一层块地址的块。
3. ext4 常用 **extent（区段）树**记录块映射，用逻辑起始块、物理起始块和长度描述一段连续块，不能把传统的直接/间接指针方案当作所有 ext 文件的固定结构。
4. inode 保存文件类型、权限、所有者、大小、时间戳、硬链接数以及内容定位信息等。不同文件类型、特性下，内容定位信息的解释也不同。
5. inode 不保存文件名。文件名属于“某个目录中的名称”，由目录项保存；这样同一个文件对象可以在不同目录中有多个名称，也便于重命名。不能仅用“文件名长度影响对齐”解释这种设计。
6. **inode number 在同一个文件系统中标识一个已分配的 inode。** 不同文件系统可以出现相同的 inode 号；inode 删除后，号码也可能被重新使用。inode 号用于定位 inode 表中的记录，数据块的位置则由该 inode 的块映射信息决定。
7. **inode 所属块组与其数据块所在块组不必相同。** 分配器尽量保持局部性，但也会根据空闲空间等情况跨块组分配。因此一个块组的 inode 用尽后，该组剩余的空闲块仍可以供其他块组的 inode 使用；若整个文件系统都没有空闲 inode，即使还有空闲块，也可能无法创建新文件。

## 文件夹（目录）

1. 目录也是文件，有自己的 inode，其内容用于组织目录项。
2. 目录项主要保存“文件名 → inode 号”的映射；文件名保存在目录中，文件对象的属性保存在对应 inode 中。
3. 查找路径时，内核从起点逐级解析路径分量：绝对路径从进程的根目录开始，相对路径通常从当前工作目录开始，`openat()` 等接口还可以指定起始目录。打开当前目录下的文件，并不需要每次从根目录重新查找当前目录。
4. 在查找某个目录中的名称时，可以通过目录项找到 inode 号，再获取对应 inode；路径查找还要处理目录搜索权限、挂载点和符号链接等情况。

### 路径缓存（目录项缓存 dcache）

1. Linux VFS 使用目录项缓存加速名称查找。这是内核通用机制，不是 ext 文件系统独有的结构；它缓存查找结果，减少反复读取和搜索磁盘目录的开销。
2. 内存中的目录项对象是 `struct dentry`，主要关联名称、父目录项和 inode。它不同于磁盘上保存的目录项记录。
3. dentry 之间具有父子关系，但名称查找通常根据“父目录项 + 名称”进行哈希查找，不是简单地遍历一棵多叉树。缓存命中时，通常仍按路径分量逐级解析，只是无需为每一级都访问磁盘。
4. 查找产生的 dentry 可以被缓存，不只缓存常用或打开次数多的文件；没有被使用的缓存项可在内存压力下回收。缓存还可以保存“该名称不存在”的结果，称为负目录项（negative dentry）。
5. 因此可以把它理解为名称查找结果的内存缓存，不能严格等同于磁盘文件树的一个子集。
