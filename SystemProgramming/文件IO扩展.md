**Linux 进程通常使用的三个标准文件描述符**

0 → 标准输入（`stdin`）  
1 → 标准输出（`stdout`）  
2 → 标准错误（`stderr`）

`stdin`、`stdout`、`stderr` 是 C 标准库的 `FILE *` 流；0、1、2 是对应的文件描述符。进程启动时它们通常已打开，但也可能被重定向或关闭。

## 文件描述符的分配

1. 在 Linux 中，`open()` 成功时返回当前进程未使用的最小非负文件描述符。
2. 如果 0、1、2 都已占用，下一次 `open()` 通常返回 3；这不是固定从 3 开始的规则。
3. 例如，关闭描述符 0 后，如果它没有被其他操作占用，下一次 `open()` 会返回 0。

## 深入理解文件描述符

1. 进程的 `task_struct` 通过 `files` 指针关联 `struct files_struct`，其中的文件描述符表保存了描述符与打开文件对象（`struct file`）的对应关系。
2. 文件描述符是进程内用于查找该表项的非负整数。同一个数字在不同进程中可以指向不同的打开文件对象；多个描述符也可以指向同一个打开文件对象。

## `dup2()` 如何实现输出重定向？

`dup2(oldfd, newfd)` 让 `newfd` 指向 `oldfd` 对应的打开文件对象。它复制的是文件描述符的引用，不是文件内容；两个描述符共享文件偏移量和文件状态标志。

例如，先用 `open()` 打开输出文件并得到 `fd`，再调用 `dup2(fd, STDOUT_FILENO)`（即 `dup2(fd, 1)`）。调用成功后，对描述符 1 的写入便会进入该文件，从而实现标准输出重定向。

1. 当 `oldfd` 有效且与 `newfd` 不同时，如果 `newfd` 已打开，`dup2()` 会先关闭它，再让它指向新的打开文件对象；关闭和复用描述符是一个原子操作。
2. 当 `oldfd == newfd` 且描述符有效时，`dup2()` 直接返回该描述符，不会将其关闭。
3. 重定向成功后，如果 `fd != STDOUT_FILENO`，通常可以关闭原来的 `fd`；描述符 1 仍然有效。应检查 `open()` 和 `dup2()` 的返回值。
4. 如果 `stdout` 中已有未刷新的输出，应在改变其底层描述符前调用并检查 `fflush(stdout)`，避免这部分输出被写到新的目标。

## 如何理解“一切皆文件”

1. 这是一种接口层面的概括：普通文件、设备文件、管道、套接字等资源中，有许多可以通过文件描述符和 `read()`、`write()` 等接口访问，但不是所有硬件或所有资源都能按普通文件的方式读写。
2. 内核使用 `struct file` 等结构表示打开的文件对象，并通过相应的文件操作实现处理请求。设备文件的操作通常会由设备驱动实现。
3. 因而用户程序可以使用相近的接口操作多种资源，但具体支持哪些操作、操作的含义是什么，取决于资源类型。

# 缓冲区机制

需要区分 C 标准库的用户态缓冲与内核中的缓存：

1. **内核缓存**：对普通文件调用 `write()` 后，数据通常先进入内核页缓存，随后再写回存储设备。`write()` 成功不等于数据已经持久化。设备、管道、套接字等资源的处理方式不同，不能一概视为“先写入磁盘缓存”。
2. **C 标准库缓冲**：`printf()`、`fwrite()` 等操作 `FILE *` 流，可能先把输出暂存在用户态缓冲区，之后再通过底层 I/O 写出。`fgets()` 等输入函数也可能预读并缓存数据。

`write()` 绕过 C 标准库的 `FILE *` 缓冲，但仍可能经过内核缓存。

## 为什么一次 `write()` 不能保证写完全部数据？

`write(fd, buf, count)` 的返回值表示实际写入的字节数，可能小于请求的 `count`，这种情况称为“部分写入”。例如，存储空间不足，或者写入过程中被信号中断，都可能导致部分写入。

处理时必须根据返回值更新位置，不能每次都从 `buf` 的开头重新写：

1. 返回正数 `n`：说明已写入 `n` 字节，将缓冲区指针向后移动 `n` 字节，并将剩余长度减少 `n`，再继续写。
2. 返回 `-1` 且 `errno == EINTR`：在本次写入任何数据之前被信号中断，可以重试本次写入。
3. 返回 `-1` 且 `errno == EAGAIN` 或 `EWOULDBLOCK`：非阻塞 I/O 当前无法写入，应等待可写后继续，避免直接忙循环。
4. 其他错误应按原因处理；如果剩余长度大于 0 却返回 0，也应停止或报告未取得进展，避免无限循环。

**写完全部字节与数据持久化是两回事**：即使循环完成全部写入，普通文件的数据仍可能留在内核页缓存中。

## C 标准库流的缓冲类型

1. 全缓冲：缓冲区满、显式刷新或关闭流等情况下输出数据。
2. 行缓冲：通常遇到换行符时输出；也可以显式刷新。
3. 无缓冲：尽快将字符传给底层接口。

`stdout` 连接终端时通常为行缓冲，重定向到普通文件时通常为全缓冲。`stderr` 默认无缓冲（准确地说，标准要求其在初始状态下不是全缓冲）；缓冲方式可以通过 `setvbuf()` 调整。

## 主动刷新缓冲区

| 函数 | 作用 | 参数 |
|---|---|---|
| `fflush()` | 将指定输出流的 C 标准库用户态缓冲数据写到底层；`fflush(NULL)` 刷新所有打开的输出流 | `FILE *` 或 `NULL` |
| `fsync()` | 同步指定文件的数据和相关元数据到存储设备；不负责刷新 `FILE *` 缓冲 | 文件描述符 `fd` |
| `fdatasync()` | 类似 `fsync()`，但只同步读取数据所必需的元数据 | `fd` |
| `sync()` | 同步整个系统中相关文件系统的待写回数据 | 无 |

如果通过 `FILE *` 向文件写入并要求数据持久化，通常先 `fflush(stream)`，再对 `fileno(stream)` 调用 `fsync()`；新建文件的目录项若也需要持久化，还需考虑同步所在目录。

正常调用 `exit()` 时会刷新并关闭打开的 C 标准库流；`_exit()` 不刷新这些流。`main()` 返回相当于调用 `exit()`，因此使用 `_exit()` 退出时，尚在 `stdout` 用户态缓冲区中的 `printf()` 输出可能丢失。

## 扩展：`fork()` 与输出缓冲

考察以下代码：

```c
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(void)
{
    const char *msg0 = "hello printf\n";
    const char *msg1 = "hello fwrite\n";
    const char *msg2 = "hello write\n";

    printf("%s", msg0);
    fwrite(msg1, 1, strlen(msg1), stdout);
    write(STDOUT_FILENO, msg2, strlen(msg2));

    fork();
    return 0;
}
```

假设这些调用成功，执行 `./hello > file` 时，文件内容的一个常见结果是：

```text
hello write
hello printf
hello fwrite
hello printf
hello fwrite
```

原因如下：

1. `stdout` 重定向到普通文件后通常为全缓冲，`printf()` 和 `fwrite()` 的内容在 `fork()` 前仍留在用户态缓冲区。
2. `write()` 不经过 `stdout` 的用户态缓冲，所以 `hello write` 在 `fork()` 前只写出一次；这不表示它绕过了内核页缓存。
3. `fork()` 复制进程的用户态内存，包括尚未刷新的 `stdout` 缓冲区。因此父、子进程各有一份待输出的数据。
4. 父、子进程从 `main()` 返回时各自刷新缓冲区，于是 `printf()` 和 `fwrite()` 的内容通常各出现两次。父、子进程的执行先后没有保证；这里两份缓冲内容相同，所以示例结果看不出顺序差异。

如果在 `fork()` 前调用 `fflush(stdout)`，待输出内容会先写出一次，子进程便不会再复制这部分未刷新的数据。
