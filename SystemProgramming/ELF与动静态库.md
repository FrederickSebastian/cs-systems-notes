# ELF文件

ELF（Executable and Linkable Format）是 Linux 等类 Unix 系统使用的二进制文件格式，主要用于以下四类文件：

1. 可重定位目标文件（通常为 `.o`，类型为 `ET_REL`）。
2. 可执行文件（传统非 PIE 可执行文件通常为 `ET_EXEC`）。
3. 共享目标文件（通常为 `.so`，类型为 `ET_DYN`；PIE 可执行文件也使用此类型）。
4. Core Dump（进程的内存与状态快照，类型为 `ET_CORE`）。

静态库 `.a` 通常是由 `ar` 打包的目标文件归档，库文件本身不是单个 ELF 文件，其中的 `.o` 成员通常是 ELF 文件。

## ELF文件结构

1. ELF Header：位于文件开头，描述文件类型、架构、入口地址，以及程序头表和节头表的位置等信息。
2. 程序头表（Program Header Table）：描述段的类型、文件偏移、虚拟地址、文件大小、内存大小、权限和对齐要求等，主要服务于加载过程。
3. 节头表（Section Header Table）：描述各节的名称、类型、大小、文件偏移和属性等，主要服务于链接与分析工具。
4. 节及其内容：例如 `.text`、`.data`、符号表、重定位信息等。`.bss` 通常为 `SHT_NOBITS`，占用运行时内存，但不在文件中存储对应的零字节。

这些部分并非按上述顺序固定排列，也不是所有 ELF 文件都具备全部部分：普通 `.o` 通常没有程序头表；运行可执行文件通常不依赖节头表，因此节头表可以被移除。参见 [elf(5)](https://man7.org/linux/man-pages/man5/elf.5.html)。

## 节与段

节（Section）是链接视角下组织代码、数据和元信息的单位，便于链接器进行符号解析、布局和重定位；并非所有节都会装入内存，例如调试信息节。

段（Segment）是执行视角下描述加载及运行信息的单位。程序头表中的 `PT_LOAD` 段指定需要映射的内容及读、写、执行权限；`PT_INTERP`、`PT_DYNAMIC` 等条目则描述解释器或动态链接信息。

> 一个可加载段可以包含多个节。链接器通常将权限相近的节组合到同一个可加载段，满足页对齐和内存保护要求。节与段是同一份文件内容的两种组织视角，不是文件中两套重复的数据。

# 动态库与静态库的选择

以下以 Linux 上的 GCC 和 GNU ld 为例：

1. 默认动态链接模式下，使用 `-lfoo` 时，链接器通常在每个搜索目录内先查找 `libfoo.so`，再查找 `libfoo.a`。搜索目录的顺序也会影响结果，不能理解为在所有目录中找到动态库后才考虑静态库。
2. `gcc -static` 用于生成静态链接的可执行文件，所需的链接依赖（包括运行时库）必须有可用的静态版本，否则通常会链接失败。
3. 选择某个静态库不必使用全局 `-static`：可以直接指定 `.a` 路径，或用 `-Wl,-Bstatic` 与 `-Wl,-Bdynamic` 切换后续 `-l` 选项的搜索模式。
4. 默认模式下，若找到的库只有静态版本，可以将其静态链接，其他库仍动态链接，这通常称为混合链接。

例如，仅将 `libfoo` 静态链接，随后恢复动态库搜索：

```bash
gcc main.o -L./lib -Wl,-Bstatic -lfoo -Wl,-Bdynamic -lbar -o app
```

静态库通常按需抽取目标文件成员，而不是把整库无条件复制到程序中。GNU ld 的传统归档搜索还受命令行顺序影响，因此通常把引用库符号的目标文件放在库选项前面。参见 [GNU ld 选项说明](https://sourceware.org/binutils/docs/ld/Options.html)。

# 静态链接

链接阶段主要完成符号解析、输入节的合并与布局、地址分配以及重定位。静态库中被选中的目标文件代码和数据会成为输出文件的一部分。

> 使用动态库的程序也要经过链接阶段，只是部分符号绑定和重定位留给运行时的动态链接器处理。

## 静态链接的全过程

1. 编译、汇编生成 `.o`，记录已定义和未定义的符号，并为尚不能确定的引用生成重定位记录。即使符号已在当前文件中定义，若最终地址或布局未确定，也可能需要重定位。
2. 链接器读取目标文件，并按需抽取静态库成员，解析符号引用与定义。
3. 链接器合并、布局输入节，确定输出节及符号的地址。
4. 链接器按照重定位类型计算结果，修正指令或数据中的相应字段；需要运行时处理的重定位则保留在输出文件中。

### 符号表

符号表不只记录被调用的函数，还可以记录变量、节、文件等符号，以及它们的类型、绑定属性、可见性、所属节、值和大小等信息。普通编译流程中，汇编器将这些信息写入 `.o`，链接器还会生成或调整输出文件中的符号表。

在可重定位文件中，普通已定义符号的 `st_value` 通常是相对于所属节起点的偏移，而不是最终虚拟地址。判断未定义符号主要看 `st_shndx == SHN_UNDEF`，不能仅看其值是否为 0，也不能把符号表的值与指令中的占位字段混为一谈。参见 [ELF ABI：符号表](https://refspecs.linuxfoundation.org/elf/gabi4+/ch4.symtab.html)。

### 重定位表

重定位记录描述需要修改的指令或数据字段，并不限于函数地址。普通 `.o` 中的重定位信息通常由汇编器生成；链接器也会生成运行时所需的动态重定位信息。

一条记录可概括为：

`| 要修正的位置 | 引用的符号（若该类型需要） | 重定位类型 | 加数 |`

重定位类型决定具体计算规则，并与处理器架构有关。`REL` 记录的加数隐含在待修正字段中；`RELA` 记录则有显式的 `r_addend`。参见 [ELF ABI：重定位](https://refspecs.linuxfoundation.org/elf/gabi4+/ch4.reloc.html)。

**为什么调用同一个函数，不同调用点填入的数值可能不同？**

以 x86/x86-64 的直接相对调用 `call rel32` 为例，指令中保存的是“目标地址 − 下一条指令地址”，不是函数的绝对地址。因此，即使目标函数地址相同，不同调用点的位移也不同。这不适用于所有指令或所有重定位类型；在 PIE 和共享库中，函数的运行时绝对地址还可能随加载基址变化。

# 动态链接

ELF 文件中的“文件偏移”“节内偏移”和“虚拟地址”是不同概念。可执行文件及共享目标文件的程序头中包含虚拟地址信息，但 PIE 和共享库的实际运行时地址通常还要考虑加载基址，不能认为文件里记录的地址一定就是本次运行的绝对地址。

## 程序启动流程

以下描述普通 Linux 用户态 C/C++ 程序的典型启动过程：

1. 执行 `execve` 后，内核根据 ELF 程序头建立可执行文件的内存映射，并建立包含参数、环境变量和辅助向量等信息的初始栈。加载过程使可加载段中“内存大小超过文件大小”的部分为零，通常用于 `.bss`；不是由 `_start` 从另一份数据段复制并清零。
2. 若文件具有 `PT_INTERP`，内核还会加载指定的动态链接器，并先将控制权交给它。动态链接器加载依赖的共享库、解析符号、处理必要的重定位，并参与初始化流程。
3. 动态链接器随后转入程序的 ELF 入口；没有解释器的普通静态可执行文件由内核直接转入其入口。常规工具链中，该入口通常是启动目标文件提供的 `_start`，并不是链接器自动生成的函数。
4. `_start` 整理调用约定所需的寄存器和栈状态，并调用 C 运行时启动逻辑。在 glibc 中通常调用 `__libc_start_main`，由相关启动代码完成初始化、调用 `main`，并在 `main` 返回后处理退出。

共享库构造函数与主程序构造函数的调用时机由动态链接器及 C 运行时协调，不能全部归给 `_start`。参见 [ELF ABI：动态链接](https://refspecs.linuxfoundation.org/elf/gabi4+/ch5.dynamic.html) 和 [glibc 的 x86-64 启动代码](https://codebrowser.dev/glibc/glibc/sysdeps/x86_64/start.S.html)。

## 动态库的加载与调用

1. 动态链接器将共享库的可加载段映射到进程的虚拟地址空间，物理页可以在发生缺页时按需装入，并不要求先把整个库读入物理内存再映射。
2. 不同进程可以共享同一库的只读代码页，但各进程的虚拟映射地址可以不同；可写数据通常通过私有映射和写时复制保持进程间独立。并不存在所有动态库都必须放入的固定“共享区”。
3. 调用共享库函数，本质上仍是进程内的函数调用：CPU 转入函数代码，函数返回后继续执行调用者。调用可能通过 PLT/GOT 间接完成，也可能采用其他形式。
4. 为避免因加载地址变化而修改代码页，位置无关代码通常使用相对寻址和 GOT 等机制，将需要运行时修改的地址集中到数据区域。代码页通常被映射为不可写；这是一种权限与共享设计，不是代码在任何情况下都无法修改。

## GOT、PLT与PIC

GOT（Global Offset Table，全局偏移量表）通常位于 `.got`、`.got.plt` 等节中，用来存放运行时需要的地址，包括全局变量地址和部分函数地址，并非只存函数跳转地址。

1. GOT 的空间与布局在链接时生成，动态链接器在运行时处理相应的重定位、填入地址；它不是由 `_start` 创建的。
2. GOT 相对于所属模块的布局在链接后通常确定，但运行时绝对地址会随模块加载基址变化，例如受 ASLR 影响。每个进程拥有自己的 GOT 数据状态。
3. PLT（Procedure Linkage Table，过程链接表）是用于外部函数调用的一组代码入口。以常见 x86-64 实现为例，调用者先调用 `foo@plt`，PLT 再通过对应 GOT 槽间接跳转到函数。
4. 若启用延迟绑定，某些函数的 GOT 槽最初指向解析路径，第一次调用时由动态链接器解析并更新，后续调用直接使用已解析地址。使用 `LD_BIND_NOW=1` 或链接选项 `-Wl,-z,now` 可以要求提前完成绑定。参见 [ld.so(8)](https://man7.org/linux/man-pages/man8/ld.so.8.html)。
5. GOT 在重定位时需要可写，但不一定始终可写：启用 RELRO 后，相应区域可被设为只读；常说的 Full RELRO 通常结合 `-z relro` 与 `-z now`，以便在提前绑定后保护 GOT。

PIC（Position-Independent Code，位置无关代码）的目标是在不同加载地址下运行而尽量避免修改代码段。`-fPIC` 用于生成适合共享库的此类代码，常见机制包括相对寻址、GOT 和 PLT，但不能将 PIC 严格定义为“相对编址 + GOT”。某些本地或隐藏符号可直接用相对寻址访问，不必经过 GOT/PLT；PIC 也不代表整个共享库无需运行时重定位，其数据和 GOT 仍可能需要修改。参见 [GCC 代码生成选项](https://gcc.gnu.org/onlinedocs/gcc/Code-Gen-Options.html)。
